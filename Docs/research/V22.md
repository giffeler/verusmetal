# VerusHash v2.2 benchmark

`make run-v22` builds and runs the complete local benchmark. `make test-v22`,
`make validate-v22`, `make sanitize-v22` and `make capture-v22` run correctness
checks, Metal validation, CPU sanitizers and an Xcode capture respectively.
For one longer-input comparison, run `./build/v22/verusbench --input-size 1487`.
Optional arguments: `--batch 4096`, `--samples 5`, `--input-size 64`.

## Implementation

The new implementation in `src/v22` was written from the algorithm's behavior;
the canonical CPU reference was inspected for compatibility. This is not a claim
of clean-room development. No third-party implementation is linked into this
benchmark, and no existing third-party Metal port was used. Algorithm constants
are shared mathematical data. The older Haraka benchmark and its licensed CPU
reference remain separate.

Each GPU thread performs input chaining, all 276 Haraka-256 key-expansion steps,
32 selector-driven CLHash steps and keyed Haraka-512 finalization. The CPU runs
the same newly written core serially, with independently written ARM AES and
PMULL primitives. GPU AES uses four pre-rotated lookup tables totaling 4 KiB;
polynomial multiplication combines four independent 32-bit partial products in
32 iterations. All eight v2.2 selector cases are implemented. The changes and
controlled comparisons are in [INSTRUCTION-OPTIMIZATION.md](INSTRUCTION-OPTIMIZATION.md).

Each hash has 8,832 key bytes plus a 64-byte finalization block in an explicit
device buffer: **8,896 bytes per hash**, about 34.75 MiB for 4,096 hashes. Vectors
are transposed across hashes for adjacent key-expansion stores. The large key is
never a private thread array. No key backup or mutation journal is needed because
each hash generates a fresh key. Random mixing loads only the selected message
vectors. Key operands are loaded within their branch, after longer AES/mix loops
where possible, to limit live ranges. Source-level scopes do not guarantee a
register count; the Xcode evidence is recorded separately.

The host uses Swift 6.4 in Swift 6 language mode, `UniqueArray` for timing records,
`RawSpan` for checked digest reads, and `InlineArray` for fixed dispatch parameters.
Xcode 27 compiles Metal language 4.0 with embedded shader sources. The benchmark
uses one classic Metal command queue for command-buffer GPU timestamps and Xcode
profiling, not the Metal 4 command-submission API. Platform features unrelated
to this compute benchmark are deliberately absent. Minimum deployment: macOS 27.

## Correctness and measurement

148 fixture digests were generated using the official portable implementation at
[VerusCoin revision 5ec1d83](https://github.com/VerusCoin/VerusCoin/tree/5ec1d83b16253aa56abda5588be76ce2d84dee8f).
It was compiled outside this project solely as an oracle. The corpus covers empty
input, block boundaries, deterministic random inputs and lengths through 2,048
bytes. CPU/GPU agreement alone would not be independent evidence because they
share the new core. The reference cache was primed before empty-input fixtures
to avoid its initial zero-seed cache hit; our implementation always builds the key.
All fixtures, partial threadgroups, repeated runs and guards pass. Metal API/GPU
validation and CPU AddressSanitizer/UndefinedBehaviorSanitizer pass.

Initial implementation measurements, before instruction optimization:
2026-09-27, Apple M4, macOS 27.0 (26A428), Xcode 27.0 (27A266a), Swift 6.4.
4,096 hashes per dispatch, 128 threads per group, 32 lanes per SIMD group;
0.75-second minimum warm-up and five alternating CPU/GPU samples. Thermal state
was nominal for every recorded sample; Low Power Mode was off.

| Input bytes | One CPU thread, MH/s | GPU, MH/s | GPU end-to-end, MH/s |
| ---: | ---: | ---: | ---: |
| 64 | 0.2342 | 0.6498 | 0.5866 |
| 1,487 | 0.1937 | 0.5938 | 0.5496 |

GPU time spans command-buffer GPU start/end, including the one compute dispatch.
End-to-end adds command creation, encoding, submission and waiting. Both include
input hashing, complete key generation, mixing and finalization; both exclude
allocation, input generation, compilation and checking. CPU and GPU do not run
concurrently. This is batch throughput, not single-hash latency.

These are short fresh-key measurements, **not mining rates**. Shared-prefix/key
caching, nonce scheduling and pool integration are absent. Haraka-only MH/s are
not comparable to full VerusHash MH/s. No speedup is attributed specifically to
Swift 6.4 or Xcode 27 without a controlled comparison against an older toolchain.
Raw samples, source/binary fingerprints, verification provenance and GPU capture
are under `build/v22`; fixtures are in `tests/v22-vectors.json`.

## Initial Xcode resource check

A separate Full / Serial / Medium replay of the 64-byte batch reports exactly
4,096 kernel invocations, **96 Temporary Registers**, **192 Allocated Registers /
High Register**, **32 Spilled Bytes**, and **9.22% Kernel Occupancy**. The register
labels are preserved as displayed, not treated as interchangeable units. Compiler
statistics show 2,642 ALU instructions. Screenshots and raw accessibility readings
are saved beside `results.json`.

The explicit device workspace bounds private state, but does **not** eliminate
spilling. This first full kernel still operates under significant register
pressure. Occupancy also depends on batch size, control-flow divergence and
instruction scheduling; it cannot be compared causally with the earlier
262,144-hash Haraka experiment. The replay uses Medium performance state and
serial profiling for counters; its duration is not substituted into benchmark
throughput. No claim of a hard 96-register hardware threshold is made.
